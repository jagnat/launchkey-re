# 22 — Euclidean arp rhythms + the accumulating mod pipeline

This note is the checkpoint after shipping our **first real code mod** (not just a data
patch) and standing up a **build pipeline that stacks mods** so they stop clobbering each
other. It explains the *why* behind both, and where we go next.

## Where we are (one paragraph)

We can now put a **Euclidean rhythm generator** into the arpeggiator, validated on real
hardware, and we have a single command — `mods/build.py` — that rebuilds a combined
firmware image with *all* our changes applied at once. The Euclidean engine is done and
proven; what's left is the **on-device UI** to select the new patterns, plus the longer
game of actually understanding the arp-page UI well enough to start replacing stock
behaviours with better ones.

## Part 1 — How the Euclidean feature happened (the RE story)

### The lucky discovery
The Launchkey arp already has a **"Rhythm"** feature (hold Arp → Rhythm row: O / OXO /
OXXO / Random / Deviate) that inserts rests into the arpeggio. When we actually read the
engine we found the thing we were about to *build* already exists in skeleton form:

- `rhythm_decode` (`FUN_080175b0`) reads `cfg[3]` (the rhythm selector) and writes a
  **bitmask** + **period** into a small state struct at `0x20001FE8`.
- `rhythm_rest_decide` (`FUN_0801760a`) is literally `return mask >> (step & 0xff) & 1;`
  — a step-indexed bitmask, with the step counter wrapping at `period`.
- The note pointer only advances on a **hit** (the manual's "Random" wording — *"on a
  rest the note is shifted to the next step, not skipped"* — told us this before we even
  read the code).

That is *exactly* the Euclidean model: a 16-step on/off mask, hit advances the melody,
rest is silence. So "add a Euclidean generator" collapsed to **"add more masks."** Stock
masks are tiny immediates: O=`1`/period1, OXO=`5`/3, OXXO=`9`/4.

### Why we measure instead of eyeballing
The device free-runs its MIDI clock (`0xF8`, 24 PPQN) and emits arp note-ons on the
**MIDI Port (ch0)**. So a rhythm is *directly countable*: clocks between note-ons =
(steps to next hit) × (clocks/step). With Latch on + a held chord it streams forever and
`scripts/midi_capture.py arp` prints a gap histogram. Every claim below was checked this
way, **before and after** each flash. Baselines:
- stock OXXO (`mask 9`, period 4) → gaps `[18, 6]` at 1/16 — matched exactly. This also
  visibly confirmed advance-on-hit (it alternated the two held notes, one per *hit*).

### Two-stage delivery
1. **Tracer bullet (n=8, 2-byte patch).** A 16-bit mask needs a `movw` (4 bytes) which
   won't fit the stock `movs` immediates — but an 8-bit mask at period ≤8 fits. So we
   repurposed the OXXO case in place: file offset `0xF5E2` `09→29` (mask = E(3,8)),
   `0xF5E4` `04→08` (period 8). No new code, selectable from the stock UI. Flashed →
   measured gaps collapsed from `[18,6]` to `{12,18}` with **zero 6-clk gaps** = E(3,8). ✅
   This proved the whole loop (RE → patch → encode → flash → measure) with near-zero risk.
2. **n=16 engine (trampoline + appended code).** For real 16-step patterns we detour the
   whole `rhythm_decode` to a reimplementation placed in the **erased flash tail**
   (`0x0801D818+`), via a 4-byte `b.w` over the function entry. The reimpl keeps the
   stock cases byte-identical and adds Euclidean presets. First flash of this (stage 2a)
   also answered the scariest unknown — **does the updater accept an image bigger than
   stock?** It does: the 88196-B image transferred (END acked) and ran; the OXO slot
   (remapped to E(4,16) for the test) measured **all 24-clk gaps** = 4 perfectly even
   hits. ✅ Image extension + hand-written Thumb trampoline + n=16 masks all confirmed.

### The masks (bit i = step i, hit on step 0)
`E(4,16)=0x1111  E(5,16)=0x1249  E(6,16)=0x2929  E(7,16)=0x2A95  E(9,16)=0x6AD5  E(11,16)=0x76DB`
Generated by the even-distribution (Bresenham) method, rotated so step 0 is a hit.

## Part 2 — The accumulating mod pipeline (why this exists)

**The problem we hit:** every experimental image was built fresh from `build/stock.bin`,
so each new mod silently dropped the previous one. We literally lost the red-LED palette
change (`session-red`) the moment we started the Euclidean work. That doesn't scale, and
it actively fights the long-term goal of layering many changes.

**The fix — `mods/build.py`:** one script, one source of truth. It loads `stock.bin`,
applies **every** mod in a manifest, and emits `build/firmware.bin` + `build/firmware.syx`.
Two kinds of mod:

- **inline** — overwrite bytes at a fixed offset (data patches like the LED palette, or
  tiny code immediates). The expected "from" bytes are *asserted against stock first*, so
  a mod can never silently land on the wrong place if an address shifts.
- **append** — assemble a Thumb `.s` file (`mods/asm/`), drop it into the flash tail at an
  **auto-allocated, 4-aligned address** (blocks stack, so many code mods coexist), and
  install a `b.w` detour over an existing function entry.

Because append addresses are allocated sequentially from the image end, adding a second or
third code mod "just works" — no manual address bookkeeping, no overlap. Everything is
verified at build time (detours and appended blocks are disassembled back out; the syx is
round-trip-decoded against the bin).

**Current manifest (`build/firmware.bin`, +148 B over stock):**
1. `led-palette-42-red` — palette idx 42 → red (recovered from `session-red-FINAL`).
2. `euclid-rhythm-engine` — detour `rhythm_decode` → keep stock rhythms 0–4 **byte-for-byte**,
   add Euclidean presets 5–10 (dormant until the UI can select them).

To build + flash the lot:
```
.venv/bin/python mods/build.py
.venv/bin/python scripts/flash.py build/firmware.syx --go   # then press Scene Launch
```

> Toolchain: Arm GNU `arm-none-eabi-as/ld/objcopy/objdump` under `/Applications/ArmGNUToolchain`.
> `.venv` has `mido` for the MIDI harness. Encode = `xkey.cli.encode(bin,"launchkey-mk3",461)`
> then patch syx bytes 6,7 = `01 02` (Mini MK3 device id). Verified bit-identical to the
> known-good `orig.syx`.

## Part 3 — The shift in strategy (why we're slowing down to go deeper)

So far we've mostly *extended* existing behaviour. The longer-term aim is **replacing**
stock features with more interesting ones, and that needs real understanding of the UI
layer, not one-byte pokes. Concretely the next target is the **arp-page UI**:

- `arp_page_render`@`0x08013508` draws the control rows (top row = group selectors
  Mode/Rate/Octave/Rhythm/Latch; only 5 of 8 top pads used). Colours come from
  `DAT_08013b00`.
- `arp_mode_select`@`0x08013B34` (+ callers `FUN_08013c84/cc2/cfc`, dispatched from
  `control_dispatch`) reads pad presses (control IDs `0x10..0x2f`) and writes the arp
  config. The active group/row lives in the UI state struct (`g_arp_state_ptr+0xc`).

The job: document this fully (it's worth its own note), then add a way to reach rhythm
selector values 5–10 — either by widening the existing Rhythm row onto its free pads, or
adding a whole new "Euclidean" group on a free top-row pad. We deliberately chose the
*bolder* path: understand the UI engine properly so future mods (custom pages, replaced
modes) are cheap.
