# 06 — Mapping the hardware from the firmware

Goal: figure out *which on-chip peripherals the firmware uses* (and therefore how
the device's hardware is wired) without a schematic. Two techniques, in increasing
rigour.

## Technique A — scan for peripheral base addresses (fast, but noisy)
On STM32, every peripheral lives at a fixed address (e.g. `RCC` = `0x40023800`,
`GPIOA` = `0x40020000`, `USB_OTG_FS` = `0x50000000`). To use one, the firmware must
load that address into a register, so the address appears as a literal 32-bit word
in the image. We scanned all aligned words and bucketed them by peripheral.

⚠️ Caveat: a random data word can coincidentally equal a peripheral base, so a
single hit is weak evidence. Treat counts as *hypotheses*, confirm with code.

## Technique B — read the code (rigorous)
`rizin` auto-analysis found **1,145 functions**. Picking the clock/GPIO code and
disassembling it confirms real usage. Example — a HAL `MspDeInit` touching
`RCC->AHB1ENR` (`0x40023830`):
```
ldr r0, [pc]        ; 0x40023830  (RCC_AHB1ENR)
ldr r1, [r0]
bic r1, r1, #4      ; clear bit 2 = GPIOCEN  -> de-inits GPIOC
str r1, [r0]
... clear bit 0     ;            = GPIOAEN  -> de-inits GPIOA
```
The `AHB1ENR` bit numbers *are* the port identities (bit0=GPIOA, bit1=GPIOB,
bit2=GPIOC, …). Reading them off is how you turn raw code into a hardware map.

## Current hardware picture
**High confidence (confirmed in code / by register semantics):**
| Peripheral | Evidence | Likely role |
|---|---|---|
| RCC | clock config + AHB1/APB1/APB2 ENR writes | system clocks |
| GPIOA/B/C/D | BSRR (`+0x18`) writes, IDR (`+0x10`) reads, ENR bits | **key/pad matrix** scan (drive columns, read rows) + button I/O |
| USB OTG FS | base `0x50000000` referenced | the **USB-MIDI** interface |
| ADC1 (+DMA) | base + SR/SQR offsets | **analog inputs**: 8 knobs, pitch/mod touch strips, maybe velocity |

**Medium confidence (address-scan hits; need xref confirmation in Ghidra):**
SPI1/SPI2 (likely the **RGB pad-LED driver** / shift registers), I2C1 (likely a
**config EEPROM** for custom modes/settings), TIM1/TIM2/TIM9 (scan timebase and/or
**LED PWM** brightness), USART1/2/6, DMA1/DMA2.

> Sanity note: `DBGMCU`/`MPU` "hits" had nonsense offsets (`+0xAF3`, `+0x440`) —
> those are false positives, discounted.

## 🔑 The headline finding: this is HAL / CubeMX code
The clock-init function fills a struct on the stack with small field values
(`2,3,4,1,…`) then calls subroutines — the exact shape of
`HAL_RCC_OscConfig(&RCC_OscInitStruct)` + `HAL_RCC_ClockConfig(...)`. The GPIO code
uses the `RCC->AHB1ENR |= bit` read-modify-write idiom of
`__HAL_RCC_GPIOx_CLK_ENABLE()`. **The stock firmware was almost certainly built
with ST's HAL, most likely generated by CubeMX.**

Why this matters:
1. Your CubeMX/HAL experience maps *directly* onto the disassembly — you already
   know what these functions are.
2. The eventual **C rebuild becomes realistic**: we're not fighting an exotic RTOS
   or bare-metal register soup; we can re-create a CubeMX project for the F401 with
   the same peripherals and reproduce behaviour function-by-function.
